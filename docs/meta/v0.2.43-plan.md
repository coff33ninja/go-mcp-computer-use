# v0.2.43 — Error Logging & GitHub Issue Reporter

## Goal
Give the AI visibility into past failures (tool errors, crashes, panics) and a way to report them to GitHub.

## Components

### 1. File-based Structured Logging (`internal/logging/`)
**New package: `internal/logging/logging.go`**

- Rotating file writer at `%APPDATA%/go-mcp-computer-use/logs/server.log`
- Max size: configurable via `log_file_max_size_mb` (default 10MB)
- Retention: configurable via `log_file_retention` (default 7 files)
- Naming: `server.log`, `server.log.1`, `server.log.2`, ... `server.log.N`
- Rotation on write when current file exceeds max size
- slog `Handler` that writes **JSON lines** (one JSON object per line) to the rotating file
- Multi-handler setup: stderr (TextHandler) + file (JSONHandler) simultaneously
- Initialized in `server.New()` after config load, before slog.SetDefault

**Config additions** (`config.go`):
- `LogFileEnabled bool` — default `true`, toggle file logging
- `LogFileMaxSizeMB int` — default `10`, max size per log file
- `LogFileRetention int` — default `7`, number of rotated files to keep
- All configurable via `set_config` at runtime (persisted to disk)

### 2. Panic Recovery Wrapper (`internal/logging/`)
- `SafeHandler(name string, fn handlerFunc) handlerFunc` — wraps any tool handler with `recover()`
- On panic: logs panic value + full stack trace to log file, returns structured MCP error
- Applied to every `mcp.AddTool` call in `server.go` — change from `handlerFunc` to `logging.SafeHandler("tool_name", handlerFunc)`
- Crash info written to log file with timestamp, tool name, panic value, stack trace

### 3. `get_logs` MCP Tool
**Registered in server.go, handler in server.go**

Parameters:
- `level` (optional): "debug", "info", "warn", "error" — filter by minimum level
- `lines` (optional): max lines to return, default 50, max 500
- `search` (optional): keyword filter (case-insensitive substring match)
- `since_minutes` (optional): only entries from last N minutes

Returns:
- Array of log entries (timestamp, level, message, attrs)
- Total matching count
- Whether truncation occurred

Implementation:
- Read last N lines from `server.log` (seek from end for efficiency)
- Parse JSON lines, filter by level/search/time
- Return structured JSON

### 4. `report_issue` MCP Tool
**Registered in server.go, handler in server.go**

Parameters:
- `title` (required): issue title
- `body` (optional): additional context from the AI
- `labels` (optional): array of labels, default ["bug"]
- `auto_logs` (optional, default true): automatically attach last 100 log lines

Returns:
- `issue_url` if `gh` CLI is available and issue created successfully
- `issue_body` (full markdown) if `gh` is not available — AI shows it to user for manual submission

Implementation:
- Generate markdown issue body with:
  - System info (OS, RAM, hostname — from existing `get_system_info`)
  - Server version
  - Recent log lines (last 100, filtered to warn/error)
  - AI-provided context
- Try `exec.Command("gh", "issue", "create", ...)` 
- If `gh` not found or fails, return the markdown body
